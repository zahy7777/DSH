# 01 · 值与类型

## 心智锚点

> [!important] 这一节要装进脑子的东西
> **JavaScript 的世界里只有两种东西：原始值（primitive）和对象（object）。** 数组、函数、日期、类实例——全都是对象的变体。这条二分法决定了后面所有的坑。

---

## 为什么需要它

你现在还没写 TS，但迟早要写这行：

```ts
const n: number = 1;
```

这行在说"`n` 这个位置放一个 `number`"。可是 **`number` 到底是什么**？它是像 Java 的 `int` 一样精确的整数，还是像 `double` 一样有精度问题？`String` 和 `string` 有什么区别？`null` 和 `undefined` 为什么是两个东西？

这些问题**不是 TS 回答的，是 JS 回答的**。TS 只是在 JS 已有的值之上，贴了一层描述。所以要学 TS 的类型，先得知道被描述的那个东西是什么形状。

这一节就干这一件事：把 JS 的"值"分成两类，看清每类的行为。

---

## 核心概念

### 1. `typeof` 只有八种可能的输出

`typeof` 是 JS 里唯一能问"这个值是什么"的操作符。它的输出**只有八种**：

| `typeof` 输出 | 是什么 | Python 对应 | Java 对应 |
|---|---|---|---|
| `"undefined"` | 未赋值 / 无值 | 无对应（`None` 是一个值） | 无对应（局部变量未初始化是编译错误） |
| `"object"` | 对象，**包括 `null` 和数组** | `dict` / `list` / 自定义实例 | `Object` 子类实例 |
| `"boolean"` | `true` / `false` | `bool` | `boolean` |
| `"number"` | IEEE-754 双精度浮点，**整数也是它** | `int` + `float` | `int`/`long`/`float`/`double` |
| `"bigint"` | 任意精度整数 | `int` | `BigInteger` |
| `"string"` | UTF-16 不可变序列 | `str` | `String` |
| `"symbol"` | 唯一且不可伪造的标识 | 无对应 | 无对应（≈ 私有 `Object` 哨兵） |
| `"function"` | 可调用对象（本质仍是对象） | 函数对象 | lambda / 方法引用 |

**注意这张表里没有的东西**：没有 `"int"`、没有 `"float"`、没有 `"array"`、没有 `"null"`、没有 `"class"`。

两个立刻会咬人的点：

- **数组的 `typeof` 是 `"object"`。** 判断数组要用 `Array.isArray(x)`。
- **`typeof null === "object"`。** 这是 1995 年第一版 JS 引擎的历史 bug：它用低位标记表示类型，对象的标记是 `000`，而空指针恰好全零。改不了了，全世界都在依赖它。

### 2. 二分法：原始值 vs 对象

把八种输出重新归类，得到这一节真正要装进脑子里的结构：

```
原始值（primitive）—— 7 种
  undefined, null, boolean, number, bigint, string, symbol

对象（object）—— 其余一切
  Array, Function, Date, RegExp, Map, Set, Promise, 以及一切 new 出来的东西
```

这不是"命名分类"，它有两条硬性行为差异：

**差异一：原始值不可变（immutable）。** 你无法"修改"一个字符串或数字，所有看起来像修改的操作都在**产生新值**：

```js
let s = "abc";
s.toUpperCase();   // 产生新字符串 "ABC"，s 本身没变
console.log(s);    // "abc"
s = s.toUpperCase(); // 这才是把新值重新绑定给 s
```

**差异二：原始值按值比较，对象按引用比较。**

```js
"abc" === "abc"        // true  —— 原始值，逐值比较
[1,2] === [1,2]        // false —— 两个不同的对象
({a:1}) === ({a:1})    // false —— 同上
```

**这条对 Java 人是舒适的，对 Python 人是陷阱。**

| | JS | Python | Java |
|---|---|---|---|
| 比较两个「值相等」的容器 | `a === b` → **false** | `a == b` → **true**（可重载 `__eq__`） | `a == b` → **false**；要 `a.equals(b)` |
| 比较是不是同一个对象 | `a === b`（同上，无法区分） | `a is b` | `a == b` |

JS 没有 Python 的 `is` / Java 的 `equals` 这层区分——**`===` 对对象永远只比身份**。想比值，得自己写比较逻辑或深比较工具。

### 3. 相等运算符：`==` 和 `===`

JS 有两个相等运算符，这是它最出名的设计失误：

- `===`（严格相等）：类型不同直接 `false`，不做转换
- `==`（宽松相等）：先做类型转换再比

实测结果见下节。结论很简单：

> **永远用 `===`。唯一的例外是 `x == null`**——这一个惯用法同时判断 `null` 和 `undefined`，是 JS 社区公认的合法用法。

TS 会主动帮你拦下 `==` 的误用（见实测三）。

### 4. 真假值（truthiness）：8 个 falsy

JS 里任何值都能当条件用。**只有 8 个值会被判为假**，其余全是真：

```
false, 0, -0, 0n, "", null, undefined, NaN
```

Python 也有真假值概念，但**容器的规则是反的**：

| 表达式 | JS | Python | Java |
|---|---|---|---|
| `[]` | **true** | **false** | 不适用（条件必须是 `boolean`） |
| `{}` | **true** | **false** | 不适用 |
| `"0"` | **true** | **true** | 不适用 |
| `0` | false | false | 不适用 |

Java 根本没有"真假值"这回事——条件位置**必须**是 `boolean`，写 `if (1)` 是编译错误。这是 Java 的一个优点，JS 和 Python 都放弃了它。

### 5. `number` 是双精度浮点，没有整数类型

**JS 只有一个数字类型：IEEE-754 双精度浮点。** 没有 `int`，没有 `long`，没有 `float`。

这意味着 Java 人对 `0.1 + 0.2 != 0.3` 的经典问题，在 JS 里是**全部数字**的问题，而不仅仅是小数的问题。整数在 ±2^53-1 之内是精确的，超出就得换 `BigInt`。

| | JS | Python | Java |
|---|---|---|---|
| 整数 | `number`（双精度，安全范围 ±2^53-1） | `int`（任意精度） | `int` / `long`（精确） |
| 小数 | `number`（同一个类型） | `float`（双精度） | `double` / `float` |
| 任意精度整数 | `BigInt` | `int` 本身就是 | `BigInteger` |
| 高精度小数 | 无内置（需库） | `decimal.Decimal` | `BigDecimal` |
| `0.1 + 0.2` | `0.30000000000000004` | `0.30000000000000004` | `0.30000000000000004` |

注意最后一行的三方结果**完全一致**——因为三者的小数都是 IEEE-754 双精度。这不是 JS 的缺陷，是浮点的本质。

**并且这个模型直接决定了 TS 的类型**：TS 里只有一个 `number` 类型，不区分整型和浮点。你没法写 `x: int`。

### 6. `string` 是 UTF-16 码元序列，不可变

JS 字符串按 **UTF-16 码元**（code unit）计数，不是按字符。一个 emoji 或生僻汉字占 2 个码元。

| | JS | Python | Java |
|---|---|---|---|
| 编码单位 | UTF-16 码元 | Unicode 码点 | UTF-16 码元 |
| `len("👍")` | `2` | `1` | `2` |
| 可变性 | 不可变 | 不可变 | 不可变 |

Java 人会觉得理所当然，Python 人会踩。要按"人眼看到的字符"数，得用 `[...s].length` 或 `Intl.Segmenter`。

### 7. 类型在运行时不存在——本节最重要的一条

TS 的 `type` 和 `interface` 是**纯粹的编译期概念，运行时被完全擦除**。它们不生成任何代码，也无法被查询。

```ts
type T = { a: number };
console.log(T);   // 编译期报错；即使绕过，运行时也是 ReferenceError
```

这就是**类型擦除（type erasure）**。它有一个直接后果，会贯穿你整个 TS 生涯：

> [!danger] 会贯穿你整个 TS 生涯的一条
> **你不能在运行时问"这个值是什么类型"。** 没有 `instanceof T`，没有 `x is T`，没有反射。
> 类型只在你写完代码到构建完成之间存在。跑起来之后，它们什么都不是。

**唯一的例外是 `enum`**：它会生成一个真实的运行时对象。这是 TS 设计里一个广受批评的不一致点，我们会在卷三展开。

## 实测

### 实测一：八种 `typeof` 与浮点真相

```js
console.log("typeof null:", typeof null);
console.log("typeof []:", typeof []);
console.log("typeof (() => {}):", typeof (() => {}));
console.log("0.1+0.2:", 0.1 + 0.2);
console.log("emoji length:", "👍".length);
console.log("MAX_SAFE_INTEGER:", Number.MAX_SAFE_INTEGER);
```

真实输出（Node v25.7.0）：

```
typeof null: object
typeof []: object
typeof (() => {}): function
0.1+0.2: 0.30000000000000004
emoji length: 2
MAX_SAFE_INTEGER: 9007199254740991
```

### 实测二：falsy 集合与对象比较

```js
const falsy = [false, 0, -0, 0n, "", null, undefined, NaN];
console.log("falsy count:", falsy.filter(v => !v).length, "/", falsy.length);
console.log('[] truthy?', Boolean([]), '| {} truthy?', Boolean({}), '| "0" truthy?', Boolean("0"));
console.log('"1" == 1 :', "1" == 1, '| "1" === 1 :', "1" === 1);
console.log('null == undefined :', null == undefined, '| null === undefined :', null === undefined);
```

真实输出：

```
falsy count: 8 / 8
[] truthy? true | {} truthy? true | "0" truthy? true
"1" == 1 : true | "1" === 1 : false
null == undefined : true | null === undefined : false
```

8 个 falsy，一个不多一个不少。空数组和空对象都是真的。

### 实测三：TS 编译器会拦住你

存成 `probe.ts`（**行号很重要，下面报错会引用它们**）：

```ts
type T = { a: number };
console.log(T);

const n: number = 1;
const s: string = "1";
if (s == n) { console.log("compared"); }

let maybe: string = null;

enum Color { Red, Green }
console.log(Color.Red);
```

用严格模式检查：

```bash
npx typescript@latest --noEmit --strict probe.ts
```

真实输出（TypeScript 7.0.2）：

```
probe.ts(2,13): error TS2693: 'T' only refers to a type, but is being used as a value here.
probe.ts(6,5): error TS2367: This comparison appears to be unintentional because the types 'string' and 'number' have no overlap.
probe.ts(8,5): error TS2322: Type 'null' is not assignable to type 'string'.
```

注意三件事：

- 第 2 行报的是「**类型不是值**」——这就是擦除在编译期的样子。
- 第 10 行的 `enum` **没有报错**，它合法且会生成真实代码。对照下一节。
- 「能不能过检查」和「能不能跑」是两台机器：`tsc --noEmit` 只检查不产出，而 Node 压根不检查。

### 实测四：擦除 vs 生成

另存一个 `erasure.ts`（**故意不含 `enum`**，原因马上说）：

```ts
type T = { a: number };
interface U { b: string }

try { console.log(T); } catch (e) { console.log("type T at runtime ->", (e as Error).message); }
try { console.log(U); } catch (e) { console.log("interface U at runtime ->", (e as Error).message); }
```

用 Node 直接跑（只擦类型、不做检查）：

```bash
node erasure.ts
```

真实输出：

```
type T at runtime -> T is not defined
interface U at runtime -> U is not defined
```

这不是编译错误，是**运行时** `ReferenceError`——类型已经被彻底删掉了，那行代码变成了引用一个不存在的变量。**类型在这些文件里从来没有存在过。**

而 `enum` 是另一回事。存成 `color.ts`：

```ts
enum Color { Red, Green }
console.log(Color, Color.Red);
```

Node 的 strip-only 模式**直接拒绝解析**：

```
SyntaxError [ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX]: TypeScript enum is not supported in strip-only mode
```

加上变换开关后它能跑，并且你会看到 `enum` **真的生成了一个对象**：

```bash
node --experimental-transform-types color.ts
```

```
{ '0': 'Red', '1': 'Green', Red: 0, Green: 1 } 0
```

**把实测四的两组输出并排看，TS 的核心矛盾就露出来了：绝大多数类型擦除得不留痕迹，少数（如 `enum`）会漏进运行时。** 这个矛盾是卷三的主线。

## 坑清单

> [!warning] 与前两门语言最容易冲突的八条
> 1. **`typeof null === "object"`** —— 历史 bug，不要试图"理解"它，记住即可。
> 2. **`typeof [] === "object"`** —— 用 `Array.isArray()` 判断数组。
> 3. **`[1,2] === [1,2]` 是 `false`** —— 对象比身份不比内容，与 Python 相反。
> 4. **`[]` 和 `{}` 是 truthy** —— 与 Python 相反。写 `if (list)` 来判断"非空"在 JS 里永远为真。
> 5. **`0.1 + 0.2 !== 0.3`** —— 只要是小数就会遇到，跟 Python/Java 一样。
> 6. **`"👍".length === 2`** —— 按码元计数，与 Java 一致、与 Python 相反。
> 7. **不要用 `==`** —— 除 `x == null` 这一个惯用法。
> 8. **类型运行时不存在** —— 别指望 `instanceof` 或反射能查出来。
